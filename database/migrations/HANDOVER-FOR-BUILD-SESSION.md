# ProjectPulse — Handover to Build Session

This replaces any earlier handover you were given. The design session has moved on a lot since then — grounded against ~30 real NRG documents and spreadsheets, not just the original vision doc.

## What ProjectPulse is (unchanged, frozen)

A **Project Intelligence Repository** for NRG Technologists (solar EPC): store every project document, extract structured data with AI, connect it across documents, and generate measurable intelligence — not a CRM/ERP/PM tool. Stack: Next.js frontend → Supabase (Postgres) → Google Drive (document storage) → OpenAI (extraction). Full detail, principles, and the reasoning behind every table: `docs/projectpulse-handover.md` in the `nrg-report-service` repo (send that file over too, or pull it if you have repo access).

## Key decisions worth knowing before you build on top of this

- **`bom_items.category` and `documents.document_type` are free text, not enums.** NRG's real category/document-type lists are long and still growing (full list now in Section 36, sourced from the handover doc's Sections 22-25) — don't hardcode a fixed set in the DB layer; keep it as an app-level reference list.
- **`material_transactions` is one shared ledger** for both BOM variance tracking (project-level) and inventory (warehouse-level) — `purchased` rows with `project_id null` are warehouse inflow; `issued_to_site`/`returned_to_warehouse` rows are project-level movement. Don't build a separate inventory table.
- **`Projects` is one table for both business lines** (residential-subsidy and commercial/industrial), distinguished by `project_type`, not two parallel schemas.
- **A project can have multiple external reference numbers** (`project_external_references`) — NRG's own internal ref, GEDA registration number, DISCOM consumer number, DISCOM SR No., etc. Never assume one `reference_number` field is enough. `reference_type` is genuinely free text as of 0012 (a real bug in 0002 had it hard-constrained to five values, contradicting its own design intent) — don't reintroduce a check constraint here.
- **Google Drive folder linking**: `projects.google_drive_folder_id` is the durable link — never derive it from folder name (real folder names follow at least 5 inconsistent patterns). New projects should auto-create their Drive folder via a service account. NRG's ~300 existing project folders need a human-reviewed import (`drive_folder_import_candidates`) — there are confirmed duplicate folders for the same project across two existing Drive locations, so this can't be a blind automatic match.
- **Never store secrets in a plain column** — monitoring-portal credentials, API keys, etc. go through Supabase Vault or equivalent, not a `text` field on `projects`.
- **No historical material-transaction data exists to import.** NRG confirmed there's no separate dispatch/purchase log — the BOM workbook's single "Actual Qty Used"/"Actual Rate" columns per line are the only record. When backfilling a historical project, create **one synthetic `material_transactions` row per `bom_items` row** (`movement_type = 'issued_to_site'`, quantity/rate from those Actual columns), with `source_document_id` set to the **same document as `boms.source_document_id`** (not a separate Delivery Challan). That's the signal that distinguishes "backfilled aggregate" from real per-dispatch data later — no extra column needed. Don't leave historical rows with zero transactions; `bom_item_variance` would then show a false "0 used" instead of "not tracked at this granularity." Historical projects therefore only ever support Material/Cost Variance, not Excess/Short Purchase or Unreturned Material breakdowns — those need sent/received/returned as separate numbers that were never recorded pre-go-live.
- **Inventory shortfall is a live query, not a batch job.** `material_shortfall` (0003) already ties together current stock, open PO quantity, and outstanding demand from every active project's `bom_items`. The moment a new project's BOM gets extracted, its `planned_quantity` rows flow straight into that view — there's no separate "check inventory" step to build, just read the view. `materials.reorder_level` is the one manually-entered field (business judgment, not AI-extracted) driving the general low-stock alert.
- **Reorder reminders need an app-layer scheduled job — the DB only tracks state, it doesn't send anything.** `reorder_alerts` (0004) exists so a daily job can check `material_stock.current_stock <= materials.reorder_level`, and only create a new alert (and fire an email/WhatsApp/push notification — build that part) when no `open`/`acknowledged` alert already exists for that material, so the same shortage doesn't nag every run. `materials.reorder_responsible_employee_id` is who to notify; fall back to a purchase-role broadcast if it's null.
- **Quote comparison is one view, not a manual lookup.** `material_quote_comparison` (0004) joins every stored `vendor_quote_items` row to `material_last_purchase`, so the reorder screen can show every quote's rate next to what was last actually paid, delta pre-computed, cheapest first.
- **Costing uses weighted-average, priced as of each issue's date** (0005), not FIFO and not a single "current average" — the latter would make a completed project's reported cost silently change every time a new purchase happens. `material_transaction_cost` handles both real per-dispatch issues (rate looked up from purchase history) and Section 28's legacy backfilled rows (rate taken directly from the row itself, since it already carries the workbook's historical Actual Rate and there may be no purchase history to look up at all for an old project). **This is not a second accounting ledger** — it's a view computed over the same `material_transactions` rows Tally also reflects, used only for BOM cost variance. Never label `actual_cost`/`cost_variance` in the UI as an accounting/valuation figure — Tally stays the sole book of record for that.
- **Never trust which Drive folder a document was uploaded into** to determine its project — a person will misfile things. AI content classification (client name, consumer number, project reference) determines the project match regardless of folder; flag a mismatch rather than trusting placement. Same principle Section 26 already established for `document_type`, now applies to project linking too.
- **A bulk purchase split across many projects needs no special handling** — one warehouse-level `purchased` row, followed by as many `issued_to_site` rows as there are projects drawing from it (each with its own quantity, and for serialized items like panels, its own slice of `serial_numbers`). `material_stock`/`material_requirement`/`material_shortfall` already aggregate correctly across any number of projects.
- **Financial Obligations is five tables, not one** (0006): `financial_obligations` (the planned/quoted layer), `sales_invoices`/`sales_invoice_items` (what's actually billed — note goods and installation are taxed at different GST rates and typically appear as separate invoice lines), `payment_receipts` (what's actually received, with the same suggested/confirmed matching pattern as everywhere else since most UPI screenshots carry no invoice reference), and `tally_ledger_entries` for reconciling against an uploaded Tally export. Quoted/Invoiced/Received/Pending are all computed via `financial_obligation_reconciliation`/`project_financial_summary`, never stored.
- **Project_Milestones covers four tracks**, not the DISCOM subsidy funnel — that's confirmed out of scope since it pays the customer directly. Each track (`geda_registration`, `discom_feasibility`, `ceig_inspection`, `site_installation`) has its own milestone vocabulary that differs by `project_type`; don't hardcode one linear sequence.
- **BOM generation for standard systems will eventually be sheet-driven, not app-code-driven** (0007): NRG already has a private Google Sheet (the "SPP Bill of Material") that correctly calculates quantities from driver inputs (panel count, rows, frame length, structure height, legs per frame, string count). ProjectPulse's job is to write those inputs to the sheet and read calculated quantities back — **never reimplement the sheet's formulas in application code**. `boms.origin` (`uploaded_workbook` vs `system_calculated`) and `boms.generation_inputs` (jsonb) exist now so a calculated BOM can be told apart from an uploaded one, but the actual Sheets API input/output cell contract is still unmapped — don't build the integration itself yet, that mapping is explicitly deferred to a later design session.
- **Rates for a system-calculated BOM come from Tally purchase history, never from any static rate sheet** — reuse `material_weighted_avg_rate`/`material_purchase_running_avg` (0005). NRG is connecting Tally live via MCP; `tally_ledger_entries.sync_source` (0007) distinguishes a live-synced row (`tally_live_sync`, no document) from an uploaded export (`manual_upload`, the 0006 default). Once live sync exists, expect most new `tally_ledger_entries` rows to have `source_document_id null`.
- **Stock statements are frozen, editable snapshots — never regenerate one from a live query** (0007). `stock_statements`/`stock_statement_items` capture `book_quantity` (system-computed, point-in-time via the new `material_stock_as_of(date)` function — **not** the live `material_stock` view, which would silently pull in later transactions), `physical_quantity` (from the monthly physical count), and `declared_quantity` (the actual number submitted to the bank — always manually editable/overridable with a note, since physical counts don't always match the system and someone has to sign off on the final figure). Valuation uses the new `material_weighted_avg_rate_as_of(material_id, date)` function, same LATERAL-join machinery as `material_transaction_cost` (0005), just point-in-time. `materials.stock_group` is a coarse reporting rollup — deliberately separate from `materials.category` (the ~15 fine-grained BOM engineering categories); don't conflate the two. Confirmed real values (stayed free text, no migration needed to set these): `dcr_panels` | `ndcr_panels` | `inverters` | `structure` | `acdb_dcdb` | `cables` | `cabling_accessories` | `hardware` | `misc` | `retail_non_project`. DCR/NDCR panels are split because only DCR qualifies for subsidy eligibility and a bank statement needs that split visible without filtering; Cables and Cabling Accessories are split too. `stock_statement_summary` view supports month-over-month comparison directly (filter by `stock_group` and two `statement_period` values).
- **Not every sale is a "project."** NRG also stocks and sells Havells heat pumps, solar dryers, solar water heaters — retail off existing stock, never installed/tracked as a project (no milestones, no BOM, no `financial_obligations` funnel). `material_transactions.movement_type` now includes `'sold_direct'` (0008) for this — always `project_id`/`bom_item_id` null — and links back to exactly which invoice line it was sold against via the new `sales_invoice_item_id` column. `sales_invoices.project_id` is now nullable with a new `customer_id` column for this case (`check (project_id is not null or customer_id is not null)`); project-linked invoices are unaffected. Different sized models (200L/300L heat pump, etc.) are just ordinary new `materials` rows — same AI-extraction-off-a-scanned-invoice flow as everything else, no special handling.
- **`document_type` is now a settled, complete reference list (0009/Section 36)**, grouped into sales & compliance, GEDA/CEIG/DISCOM chain, engineering drawings, inventory/material movement, financial reconciliation, KYC/compliance checklist, and visual. Two direction-ambiguous types were split rather than given a schema column: `purchase_order_customer` vs. `purchase_order_vendor` (same document label, opposite direction — Section 24). `payment_proof` covers receipt book/cheque photo/UPI screenshot/bank excerpt as one type, since the method is captured on `payment_receipts.payment_method`, not the document. **Document type/template alone cannot reliably determine movement direction** for `material_out`/`material_in`/`delivery_challan`/`gate_pass` — a Gate Pass pad is used for both directions, disambiguated only by a handwritten note — extraction has to read content, not trust the label. The KYC types (`pan_card`, `aadhaar_card`, `gst_certificate`, etc.) populate nothing beyond `documents` itself; they're checked off against a `required_documents` reference list per `project_type` at the app layer — no new table, that's a query against what's already uploaded, not stored state.
- **`electrical_test_records` (0009)** is a new dedicated table for the CEIG Test Inspection Application + Inspection Report pair — genuinely measurable, fixed-shape facts (Megger readings, earth pit resistance across typically 4 pits, contractor/supervisor license numbers), not generic AI Facts rows. `file_no` links the two documents (`application_document_id`/`report_document_id`). `status = 'satisfactory'` is the trigger event for the CEIG track's completion milestone in `project_milestones` — same role the GEDA Registration Letter plays for `geda_registration`. `issuing_authority` is free text on purpose — approval authority is regional/scale-dependent, not always the Chief Electrical Inspector.
- **`documents.project_id` is now nullable (0009)** — it was `not null` since it was first drafted, which silently made it impossible to store a warehouse-level purchase document or a direct-sale invoice (both legitimately projectless). Fixed to match `sales_invoices.project_id`'s already-nullable shape.
- **New `material_transactions` columns (0009)**: `dcr_ndcr_status` (Domestic Content Requirement status per purchase batch — affects government-scheme eligibility), `batch_ref_no` (NRG's own fiscal-year + type-letter + sequence identifier, e.g. `18-19-P-01`, matching their existing internal procurement logs), and a self-referencing `replaces_transaction_id` for warranty replacements — a real case exists where a new serial supersedes a failed one against the same project.
- **A known architectural gap you should flag to the design chat**: this session's `profiles`/auth table and the design chat's `employees` table haven't been reconciled — decide whether they're the same entity (`employees.employee_id = auth.users.id`) or `employees` is a superset with an optional `auth_user_id`, before building anything that depends on "who is this person."
- **Delivery Challans are now generated, not just scanned (0010) — this is the highest-priority piece of everything in this handover.** Opening "generate DC" for a project should pre-fill line items from `bom_items.planned_quantity` minus what's already gone out net of returns — never a blank form. The generated PDF becomes the `documents` row (`delivery_challans.generated_document_id`) and the `material_transactions` `issued_to_site` rows (`delivery_challan_id` set) simultaneously — there's no separate extraction step for a system-generated DC, only for the rare handwritten paper-book fallback (which leaves `delivery_challan_id` null). `document_number_sequences`/`next_document_number()` gives controlled, gapless-per-series numbering — reuse it if/when PO generation happens later, don't build a second numbering mechanism.
- **Commissioning Report generation is two-sided, not one (0010)** — unlike the DC, NRG's real commissioning report is a **prefilled printed template that gets handwritten readings added on-site, then re-uploaded**. So `commissioning_reports` needs both a generation flow (produce `template_document_id`) and an extraction flow (read `filled_document_id` back into the structured fields) — don't build only one half. A confirmed report should flip `projects.status` to `'commissioned'`.
- **PO generation is confirmed not critical** — most vendor POs are just phone calls today. Don't prioritize building a PO-generation UI; `purchase_orders` (0003) already works fine for logging POs after the fact.
- **`project_costs` (0011) is capture-only, not a margin report.** Vendor/transport bills usually don't mention a project, so they land as `assignment_status = 'unassigned'` and MP assigns them by hand — same pending-until-resolved pattern as `payment_receipts.match_status`. `'general'` is a real, distinct outcome (e.g. one transport bill covering three residential dispatches on one truck) — never collapse it with `'unassigned'`; one means "not looked at yet," the other means "looked at, correctly belongs to no single project." **Do not build a margin/profitability view against this yet** — margin is explicitly still being defined in the design chat; this migration only makes sure the cost data exists and is properly attributed before that conversation happens.
- **`customers.aliases` (0012)** — same pattern as `materials.aliases`. Real case: an electricity bill shows the legal owner's name while the whole team refers to the project by its business name. `name` stays the primary/display name; `aliases` holds every other variant, and both should be checked when matching an incoming document to a customer.
- **Compliance milestone vocabulary is richer than what shipped so far — no schema change, just use the fuller list.** `geda_registration`: `application_submitted` → `fees_paid` → `registered`. `discom_feasibility`: DISCOM's SR No. goes in `project_external_references` (`reference_type = 'discom_sr_no'`), then `estimate_paid` → `feasibility_generated`. `ceig_inspection`: five steps confirmed, not three — `applied` → `sld_approved` → `test_inspection_applied` → `satisfactory_letter_received` → `certificate_received` (the satisfactory letter and the final certificate are two separate documents/events).
- **Fabricator/electrician per project already has a home — `project_milestones.vendor_id`.** Populate it on the relevant `site_installation` steps (structure/panel-fitting steps → the fabricator partner; inverter/ACDB-DCDB/earthing steps → the electrician partner) rather than adding a new column. Surface it on the Project Overview as a plain "Team" line so nobody has to dig through individual milestone rows to find it.
- **The financial visibility boundary is narrower than first stated — corrected in Section 39.** The obligation ledger (`financial_obligations`/`sales_invoices`/`payment_receipts` reconciliation — Quoted/Invoiced/Received/Pending) is visible to **everyone** (Sales, Sales-backend, Service, Purchase, Owner) — it's operationally necessary, e.g. MP checking payment status before releasing a dispatch. Only cost/margin is owner-only: `bom_item_variance.actual_cost`/`cost_variance` specifically (quantities on the same BOM rows stay visible to everyone), `project_costs` in aggregate, and any future margin view. A bill in `project_costs` is still visible to MP while they're actually assigning it — the restriction is on the aggregated cost view, not on someone doing their job. **This applies to menus too, not just data**: a report/tab a role can't see should be absent from the UI entirely, not shown locked/greyed — don't announce that something exists if the role can't have it.
- **Vendor quote rates aren't always comparable as raw numbers (0013).** `includes_transport`/`includes_loading_unloading`/`notes` on `vendor_quote_items` — null on all three means "not specified" (a common, legitimate case for a phone-quoted rate), not missing data. The comparison screen should show these flags next to the rate rather than silently ranking cheapest-first as if every quote were on equal terms.
- **`materials.make` (0013) — a real, named gap: Sales was quoting Waree 620W while Adani 620W sat in stock.** The old `unique(category, canonical_name)` constraint is now `unique(category, canonical_name, make)` — two brands at the same wattage are two distinct materials rows. Also a permissions note: Sales needs read access to stock levels by material even though they do almost no document processing in ProjectPulse itself.
- **Capacity Consistency Check needs a tolerance band, not exact-match** — quoted vs. as-purchased wattage naturally drifts a little (manufacturing "Wp binning," e.g. quoted 620W, received 615W) and that's not an error; disagreement *across government documents* (Quote/GEDA/Feasibility/Registration) should still be flagged at zero tolerance. Report logic only, no schema.
- **The approval threshold is ₹25,000, confirmed real (0015).** `quote_comparison_requests.total_amount` is snapshotted at submission, not recomputed live — so the number the owner gets notified about can't drift if quotes change after the fact. Above ₹25,000, notify the owner on `draft → submitted`; below it, MP can self-clear. `submitted → approved` notifies MP a PO can be raised. Both are app-layer jobs, same pattern as `reorder_alerts` — don't build DB triggers for this, the state transition is all the DB provides.
- **Vendor rates need a landed-cost estimate, not just a yes/no flag (0015).** When `includes_transport`/`includes_loading_unloading` (0013) is false, MP fills in `vendor_quote_items.estimated_transport_charge`/`estimated_loading_unloading_charge` so the comparison can rank by effective landed cost (`rate × qty + both estimates, nulls as zero`), not the printed rate — otherwise the vendor who excluded the most from their number always looks cheapest.
- **`partners.supplies_categories` (0015) is a manual tag, not a substitute for real history.** Only useful for a vendor with no order history yet — a vendor who's actually been quoted or bought from should be found by joining `vendor_quote_items`/`material_transactions`, not this array.
- **`employees` (0002) already covers the editable People roster** — name/role/phone/email/active is exactly what an Owner/MD, Maintenance, Engineer, Accounts, Purchase list needs. When someone leaves: update their row with the replacement's details, or set `active = false`. **Never delete an employee row** — `confirmed_by`/`sales_person_id`/`assigned_by`/etc. across this entire schema point at `employee_id`, and a delete orphans that history.
- **"Order Now" is now a real view column, `material_shortfall.order_now` (0016) — read it, don't recompute it in the UI.** Confirmed formula: `current_stock + open_order_quantity + reorder_level − outstanding_requirement`. Negative means order it. The existing `shortfall` column stays too (a different, still-useful question — requirement vs. supply with no safety buffer folded in); don't conflate the two. The PO lifecycle already zeroes `order_now` out correctly with nothing new to build — `material_open_orders` (0003) already nets ordered quantity against what's actually been received.
- **A sheet-generated BOM needs two sign-offs before it drives ordering, not one (0016).** Engineer confirms first (existing `extraction_status`/`confirmed_by`/`confirmed_at`), then `boms.owner_approved_by`/`owner_approved_at` is a separate second tick. `material_requirement` now only counts a BOM's `planned_quantity` once `extraction_status = 'confirmed'` **and** (`origin = 'uploaded_workbook'` **or** `owner_approved_at is not null`). The carve-out matters: an uploaded workbook is already a human-authored document and only needs the one existing confirmation — don't require owner approval on those too, that would silently zero out every historical BOM's contribution to ordering the moment this ships. The second tick is only for `origin in ('system_calculated','recommendation_engine')`.
- **Three scheduled digest emails, confirmed requirements — app-layer cron jobs, no new schema.** Each is one digest email, not one per row: **What Needs Ordering** (`material_shortfall` where `order_now < 0`) → `purchase@nrgtechnologists.com` + owner, daily 8:00am. **Stock Statement** (`stock_statement_summary`, latest period) → purchase + owner, weekly Saturday 3:00pm. **Required Documents Gap** → `sales@nrgtechnologists.com` + `service@nrgtechnologists.com` + owner, daily 8:00am. Same pattern as `reorder_alerts` — the views already answer these live, this is a scheduling/templating task.
- **Quote comparison needs an approval gate before it can become a PO (0014).** `vendor_quotes.is_selected`/`purchase_order_id` (0004) technically already let a quote convert straight to a PO — the missing piece was ever requiring a sign-off first. `quote_comparison_requests` batches 2-4 vendor quotes (one or several materials) under one decision: MP builds it in `'draft'`, flips to `'submitted'`, owner sets `'approved'`/`'rejected'` with `decision_notes`. Enforce at the application layer: only an `'approved'` request should let the app set `is_selected` or create a `purchase_orders` row. Sending the comparison for approval (email/WhatsApp/push) is your job to build — the DB only tracks state.
- **Vendors are `partners` with `category = 'vendor'` — don't build a separate vendors table.** `partners.contact_person` (0014) is the one field that was missing (name/phone/email/GSTIN/address already existed since 0002).
- **`stock_statement_summary` was missing `materials.make` (0014)** — recreated via `create or replace view` since `make` (0013) landed after this view was first written. A real bank statement needs Adani 545W and Waree 545W as separate lines, not folded into one panel total.
- **Cross-checked the real SPP Bill of Material sheet — `materials.make` already covers it, no schema gap.** Confirmed real panel brands across ~30 project tabs: Adani, Waree, Goldi (wattages 540-725 depending on vintage). Confirmed real inverter brands: Growatt (dominant), Goodwe. Useful for seed/demo data — a `materials` row should never be just "Solar Panel," it's always make + wattage as separate rows (e.g. `Adani 615W`, `Waree 615W` are two different `material_id`s, same as `Adani 545W` vs. `Waree 545W` already established in 0013).
- **The BOM Recommendation Engine (0013) is done — the last big item on the original Next Session list.** `material_consumption_benchmark` computes `used_qty_per_kw` per material from **`commissioned`** projects only (a still-dispatching project would skew the benchmark low) using real `bom_item_variance.used_quantity` (dispatched minus returned), not planned quantity — that's the entire point, learning from what actually happened on site, not what was estimated. `project_sample_size` should drive the recommendation's own confidence — 1-2 historical projects is a guess, 10+ is a real pattern. A generated BOM from this is ordinary `bom_items` rows with `boms.origin = 'recommendation_engine'` (a new third value alongside Section 33's `'system_calculated'`), reviewed and confirmed like everything else — never auto-applied. Coexists with, doesn't replace, Section 33's sheet-driven path.

The document processing workflow itself (trigger → classify → extract → write, retry/failure handling, human-review queue for low-confidence extractions — the taxonomy this workflow runs against is now settled, see Section 36), user roles/permissions + Row-Level Security policies (design these before real users touch the app — retrofitting RLS later is expensive; the financial visibility boundary above is already decided, RLS just needs to enforce it at the database level, not just hide it in the UI), an audit log for manual edits (separate from the AI extraction_status pattern already in place), BOM Recommendation Engine, Marketing module, margin/profitability reporting (deferred until margin is properly defined — see `project_costs` above), a report aggregating `project_milestone_durations` across all projects to find systemic bottlenecks (no new schema needed, just a cross-project view), and a suggested-reorder-level mechanism (compute from consumption rate × lead time, same `ai_extracted`/`confirmed` pattern as everything else, rather than pure manual entry). Also worth planning for, not urgent yet: soft-deletes/retention policy for financial and KYC documents (Aadhaar/PAN cards are in scope as Documents — this has real Aadhaar Act / DPDP Act implications, not just a nice-to-have), and idempotency in the AI extraction pipeline so a retried/duplicate document upload can't create duplicate `bom_items`/`material_transactions` rows.
